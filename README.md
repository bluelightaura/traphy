# TRaphy

**traffic + Scapy.** Собираешь кадр руками в терминале, подключаешься к машине,
выбираешь порты из тех, что там реально есть, - а трафик программа конфигурит и
гонит скриптом. Скрипт при этом настоящий: самодостаточный `.py`, его видно до
запуска, можно сохранить и гонять потом без TRaphy вообще.

```
╭──────────────────────────────────────────────────────────────╮
│ ◈ TRaphy 0.1.0                                               │
│   собрать трафик руками - погнать его скриптом               │
├──────────────────────────────────────────────────────────────┤
│ Цель: root@10.0.0.9 · ens1f0                        (Scapy)  │
│   ✓ связь есть: bench01 · ens1f0                             │
│   Профиль: ip_sweep · 1 из 1 потоков · 5 000 pps             │
│   ↻ прошлый прогон: ip_sweep · 2026-09-01 16:41              │
│                                                              │
│    Настроить цель         хост, интерфейсы, связь            │
│  ▸ Собрать трафик         пресет или по слоям                │
│    Потоки профиля         править, включать, диапазоны       │
│    Показать скрипт        то, что уйдёт на хост              │
│    Сухой прогон           собрать кадры, ничего не слать     │
│    Запустить              погнать трафик и смотреть счётчики │
│    Сохранить скрипт       положить .py рядом                 │
│    История прогонов       что и когда гнали                  │
│    Язык                   RU                                 │
│    Тема                   тёмная                             │
│                                                              │
│   ↑/↓ выбор   ↵ пуск   q выход                               │
╰──────────────────────────────────────────────────────────────╯
```

## Как это работает

1. **Собираешь трафик.** Пресет или по шагам: слой (L2 / L3 / L4) → поля кадра
   (MAC, VLAN, IP, TTL, порты, размер) → что перебирать → скорость и режим.
2. **Настраиваешь цель.** Локально или по SSH. Нажимаешь `c` - TRaphy лезет на
   машину и приносит оттуда список интерфейсов с MAC, состоянием и скоростью,
   версию Python, есть ли Scapy и получится ли взять root. Порты выбираются из
   этого списка.
3. **Смотришь скрипт.** Тот самый файл, который уедет. Не пересказ формы.
4. **Гонишь.** Скрипт уезжает на цель, запускается там и построчно отдаёт
   счётчики обратно; на экране tx / rx / потери / реальная скорость.
5. **Читаешь итог.** Профиль, скрипт, поток событий и результат складываются в
   каталог прогона - цифру из отчёта через неделю можно проследить до кадров.

## Установка

```sh
git clone https://github.com/bluelightaura/traphy && cd traphy
python -m venv .venv && . .venv/bin/activate
pip install -e .            # меню, модель и генератор - только стандартная библиотека
pip install -e '.[ssh]'     # + удалённые цели по SSH
traphy                      # или: python -m traphy
```

**Scapy нужен на цели, а не здесь.** На машине, где открыто меню, он не нужен
вообще: TRaphy собирает и показывает скрипт без него. Отправляет - цель, и там
же нужны root или `sudo` без пароля.

## Из командной строки

Всё то же самое, теми же функциями, без меню:

```sh
traphy presets                                  # что есть готового
traphy gen ip_sweep -o sweep.py                 # собрать скрипт
traphy probe -t bench                           # что на цели: NIC, root, scapy
traphy run ip_sweep -t bench -d 30              # прогнать
traphy run l4_tcp -t bench --dry-run --json     # собрать кадры, ничего не слать
traphy history -n 20
```

Сохранённый скрипт живёт своей жизнью:

```sh
sudo ./sweep.py --iface ens1f0 --rx-iface ens1f1 --duration 30
```

## Пресеты

| Ключ | Что гонит | Обо что бьёт |
|---|---|---|
| `l2_ethernet` | чистые Ethernet-кадры | коммутация, MAC-таблица |
| `l2_vlan` | тегированные кадры | транк, per-VLAN forwarding |
| `l3_ip` | IPv4 | маршрутизация, FIB |
| `l4_udp` / `l4_tcp` | UDP / TCP | ACL, сессии, NAT |
| `imix` | 64/590/1514 в 7:4:1 | смесь, похожая на живой трафик |
| `ip_sweep` | перебор IP назначения по /24 | таблица маршрутов |
| `port_sweep` | перебор порта назначения | сессии, NAT, ACL |
| `table_stress` | случайные источники на высоком pps | таблицы под нагрузкой |
| `burst_probe` | очереди с паузами | буферы, микробёрсты |

Любой из них - стартовая точка: открывается в редакторе потоков и правится.

## Про честность цифр

Инструмент, который печатает «потери 0%», когда никто ничего не считал, хуже
бесполезного. Поэтому:

* **Потери меряются только если задан интерфейс приёма.** Без него в отчёте
  стоит «приём не измерялся», а не ноль. Считаются кадры с меткой прогона -
  метка своя на каждый запуск, чтобы не поймать хвост предыдущего.
* **Скорость - цель, а не гарантия.** Scapy через сокет ядра выдыхается
  где-то в районе десятков тысяч кадров в секунду. Скрипт печатает ту скорость,
  которую реально выдал, и если она заметно ниже запрошенной - это сказано
  вслух: устройство на этой скорости не проверено.
* **Урезанные диапазоны названы.** Перебор по /16 - это 65 тысяч кадров;
  генератор режет до 1024 и говорит, что урезал, а не молча шлёт часть.

## Движки

Модель трафика - одно, чем его выдувать в кабель - другое. Транспорт, опрос
хоста, архив прогонов и меню общие; движок меняет только артефакт и то, чем он
запускается.

| Движок | Слои | Состояние |
|---|---|---|
| **Scapy** | L2-L4 | работает |
| **TRex** | L2-L4 | заявлен: DPDK, линейная скорость, потери по flow stats |
| **JMeter** | L7 | заявлен: потоки, запросы, задержки |

TRex и JMeter уже выбираются в настройке цели и честно отвечают, чего им не
хватает на этом хосте, - но гнать через них пока нельзя. Что каждому нужно -
ниже, в «Будущих релизах»; то же самое расписано в `src/traphy/engines/trex.py`
и `src/traphy/engines/jmeter.py`.

## Что внутри

```
src/traphy/
  models.py        Profile / Stream / Packet / VMField - вся модель трафика
  presets.py       готовые профили
  codegen.py       Profile → самодостаточный Scapy-скрипт
  target.py        цель: хост, интерфейсы, движок; хранилище целей
  transport.py     доставка скрипта: локально или по SSH
  probe.py         что есть на цели: NIC, root, Scapy, Java
  runner.py        один прогон: собрать, отправить, разобрать счётчики, записать
  engines/         шов под Scapy / TRex / JMeter
  ui.py            панели, темы, чтение клавиш - только стандартная библиотека
  menu.py          лаунчер
  screens/         настройка цели, сборка трафика, прогон, история
```

Тесты гоняют движок отправки на подменённом Scapy - темп, очереди, смешивание
потоков, перенос по диапазону и подсчёт приёма проверяются без root и без NIC:

```sh
pip install -e '.[dev]' && pytest -q && ruff check src tests
```

## Будущие релизы

Главное, что планируется, - два движка рядом со Scapy. Шов под них уже стоит:
транспорт, опрос хоста, архив прогонов и меню общие, движок меняет только
артефакт и то, чем он запускается. Оба уже выбираются в настройке цели и
честно отвечают, чего им не хватает на хосте.

### TRex

Scapy через сокет ядра выдыхается где-то в районе десятков тысяч кадров в
секунду. Выше этого прогон рассказывает про генератор, а не про железку, - и
вот тогда DPDK окупает свою сложность. TRex ещё и потери меряет по-настоящему:
flow stats считаются в железе, а не сниффером по метке в payload, так что его
цифру можно класть в отчёт без оговорок.

Что для этого нужно:

* профиль в форме самого TRex - `STLStream` в `STLProfile`, скорости через
  `STLTXCont` / `STLTXSingleBurst` / `STLTXMultiBurst`, а диапазоны как
  переменные field engine, а не развёрнутые кадры (модель в `models.py` под
  это уже разложена - потому диапазоны и названы VM-полями);
* его собственный Scapy: смещения полей, куда пишет field engine, считаются
  против пропатченного Scapy из релиза TRex, поэтому кадры надо собирать на
  хосте и его интерпретатором;
* демон вместо команды: TRex живёт сервером, прогон - это подключиться,
  захватить порты, загрузить профиль, стартовать, читать статистику, снять;
* порты вместо интерфейсов: NIC отданы в DPDK и адресуются индексом, имена из
  `/sys/class/net` перестают быть нужным идентификатором.

### JMeter

Scapy и TRex отвечают на вопрос «пропускает ли железка кадры и на какой
скорости ложится». JMeter отвечает на другой - «держит ли сервис за ней N
клиентов с настоящими запросами», - и этот вопрос возникает на тех же стендах,
против тех же целей, обычно сразу после ответа про L2-L4.

Что для этого нужно:

* другая единица нагрузки: не кадры и pps, а thread groups - сколько потоков,
  ramp-up, циклы или длительность, и сам запрос: метод, URL, заголовки, тело.
  `Packet` про это ничего сказать не может, так что рядом встанет своя
  маленькая модель, а не растянутый поверх слой;
* артефакт `.jmx`, а не скрипт: тот же XML, что пишет GUI, чтобы собранный
  здесь план открывался в самом JMeter. В этом и смысл - это должен быть
  настоящий план, а не что-то, запускаемое только этим инструментом;
* другой запуск: `jmeter -n -t plan.jmx -l results.jtl` и JVM на хосте;
  прогресс придётся разбирать из вывода саммарайзера или из `.jtl` по мере
  записи, а не печатать из своего же кода;
* другие счётчики: запросы, ошибки, перцентили задержек и throughput вместо
  tx / rx / потерь. Правило честности остаётся тем же: перцентиль с прогона,
  который не вышел на заданную нагрузку, описывает генератор, а не сервис.

### Что ещё в очереди

| Что | Зачем |
|---|---|
| Перебор MAC | сейчас таблица коммутации нагружается через источники IP; настоящий перебор даст честный стресс CAM |
| Задержка и джиттер | метка времени в payload, чтобы мерить не только потери |
| IPv6 | модель пока только IPv4 |
| Настоящие сессии TCP | сейчас это кадры с флагами, а не установленные соединения |
| Двусторонний прогон | гнать с обеих сторон одновременно и сводить результат |
| Сравнение прогонов | базовый против текущего, чтобы видеть регрессию железки, а не только абсолютные цифры |
| Цели не только Linux | интерфейсы читаются из `/sys/class/net` |
