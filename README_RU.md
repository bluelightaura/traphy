# TRaphy

![TRaphy — builds the frame and blows it down the wire](assets/traphy-banner.png)

[English version](README.md)

*traffic + Scapy*

Каждый раз одно и то же: надо посмотреть, как свитч переживёт перебор IP по
/24, - и опять пишешь одноразовый скрипт на Scapy, опять вспоминаешь, как там
интерфейс называется, опять забываешь про паддинг до нужного размера кадра.

Теперь так: собрал кадр в меню - слой, MAC, VLAN, IP, порты, размер, что
перебирать, с какой скоростью. Ткнул в железку, выбрал порты из того, что там
реально нашлось. Нажал «запустить» - скрипт сам собрался, уехал на хост и
погнал, а счётчики вернулись на экран.

Скрипт при этом не спрятан. Его видно до запуска, целиком, и можно забрать
себе: обычный `.py`, работает и без TRaphy.

```
╭──────────────────────────────────────────────────────────────╮
│ ◈ TRaphy 0.1.0                                               │
│   собрать трафик руками - погнать его скриптом               │
├──────────────────────────────────────────────────────────────┤
│ Цель: root@10.0.0.9 · ens1f0                        (Scapy)  │
│   ✓ связь есть: bench01 · ens1f0                             │
│   Профиль: ip_sweep · 1 из 1 потоков · 5 000 pps             │
│   ↻ прошлый прогон: ip_sweep · 2026-09-01 16:41              │
│                                                              │
│    Настроить цель         хост, интерфейсы, связь            │
│  ▸ Собрать трафик         пресет или по слоям                │
│    Потоки профиля         править, включать, диапазоны       │
│    Показать скрипт        то, что уйдёт на хост              │
│    Сухой прогон           собрать кадры, ничего не слать     │
│    Запустить              погнать трафик и смотреть счётчики │
│    Сохранить скрипт       положить .py рядом                 │
│    История прогонов       что и когда гнали                  │
│    Язык                   RU                                 │
│    Тема                   тёмная                             │
│                                                              │
│   ↑/↓ выбор   ↵ пуск   q выход                               │
╰──────────────────────────────────────────────────────────────╯
```

## Как это работает

1. **Собираешь трафик.** Пресет или по шагам: слой (L2 / L3 / L4) → поля кадра
   (MAC, VLAN, IP, TTL, порты, размер) → что перебирать → скорость и режим.
2. **Настраиваешь цель.** Локально или по SSH. Нажимаешь `c` - TRaphy лезет на
   машину и приносит оттуда список интерфейсов с MAC, состоянием и скоростью,
   версию Python, есть ли Scapy и получится ли взять root. Порты выбираются из
   этого списка.
3. **Смотришь скрипт.** Тот самый файл, который уедет. Не пересказ формы.
4. **Гонишь.** Скрипт уезжает на цель, запускается там и построчно отдаёт
   счётчики обратно; на экране tx / rx / потери / реальная скорость.
5. **Читаешь итог.** Профиль, скрипт, поток событий и результат складываются в
   каталог прогона - цифру из отчёта через неделю можно проследить до кадров.

## Установка

Один вход - скрипт `start`: он сам создаёт окружение, ставит зависимости и
запускает. Ставить что-либо руками перед этим не нужно.

```sh
git clone https://github.com/bluelightaura/traphy && cd traphy
./start                     # меню
./start presets             # любая команда - аргументы уходят как есть
```

Чтобы звать откуда угодно одной командой, как `code` или `opencode`:

```sh
ln -s "$PWD/start" ~/.local/bin/traphy
traphy                      # меню
traphy run ip_sweep -t bench -d 5
```

Переустановка происходит сама, когда `pyproject.toml` оказывается новее отметки
в `.venv`; в остальное время запуск мгновенный.

Пароли `start` подхватывает из `~/.config/traphy/secrets.env`, если файл
заведён (путь переопределяется через `TRAPHY_SECRETS`) - `TRAPHY_SSH_PASSWORD`,
`TRAPHY_SUDO_PASSWORD`, `TRAPHY_IXIA_PASSWORD`. В репозиторий они не попадают:
он публичный, а файл лежит вне него.

Если окружение хочется собрать самому:

```sh
python -m venv .venv && . .venv/bin/activate
pip install -e .            # меню, модель и генератор - только стандартная библиотека
pip install -e '.[ssh]'     # + удалённые цели по SSH
pip install -e '.[ixia]'    # + шасси Ixia: клиент IxNetwork нужен здесь
traphy                      # или: python -m traphy
```

**Scapy нужен на цели, а не здесь.** На машине, где открыто меню, он не нужен
вообще: TRaphy собирает и показывает скрипт без него. Отправляет - цель, и там
же нужны root или `sudo` без пароля.

## Из командной строки

Всё то же самое, теми же функциями, без меню:

```sh
traphy presets                                  # что есть готового
traphy gen ip_sweep -o sweep.py                 # собрать скрипт
traphy gen ip_sweep --engine trex -o sweep.py   # то же, но для TRex
traphy gen ip_sweep --engine ixia -o sweep.py   # то же, но для шасси Ixia
traphy probe -t bench                           # что на цели: NIC, root, scapy
traphy run ip_sweep -t bench -d 30              # прогнать
traphy run l4_tcp -t bench --dry-run --json     # собрать кадры, ничего не слать
traphy history -n 20
```

Сохранённый скрипт живёт своей жизнью:

```sh
sudo ./sweep.py --iface ens1f0 --rx-iface ens1f1 --duration 30
```

## Пресеты

| Ключ | Что гонит | Обо что бьёт |
|---|---|---|
| `l2_ethernet` | чистые Ethernet-кадры | коммутация, MAC-таблица |
| `l2_vlan` | тегированные кадры | транк, per-VLAN forwarding |
| `l3_ip` | IPv4 | маршрутизация, FIB |
| `l4_udp` / `l4_tcp` | UDP / TCP | ACL, сессии, NAT |
| `imix` | 64/590/1514 в 7:4:1 | смесь, похожая на живой трафик |
| `ip_sweep` | перебор IP назначения по /24 | таблица маршрутов |
| `port_sweep` | перебор порта назначения | сессии, NAT, ACL |
| `table_stress` | случайные источники на высоком pps | таблицы под нагрузкой |
| `burst_probe` | очереди с паузами | буферы, микробёрсты |

Любой из них - стартовая точка: открывается в редакторе потоков и правится.

## Про честность цифр

Инструмент, который печатает «потери 0%», когда никто ничего не считал, хуже
бесполезного. Поэтому:

* **Потери меряются только если есть чем.** Без интерфейса приёма в отчёте
  стоит «приём не измерялся», а не ноль. На Scapy считаются кадры с меткой
  прогона - метка своя на каждый запуск, чтобы не поймать хвост предыдущего.
* **Рядом с цифрой приёма написано, чем её померили.** Источников несколько,
  и они стоят разного: `flow stats` у TRex и `traffic item` у Ixia - счётчики
  в железе, их можно класть в отчёт как есть; `метка` - это сниффер, ловящий
  наш признак в теле кадра; `счётчик порта` складывает всё, что в него
  прилетело, а не только наши кадры; `частично`
  значит, что часть потоков ушла без счёта; `не измерялся` - что не считал
  никто.
  Ноль в колонке потерь, который на деле означает «никто не смотрел», - самое
  дорогое враньё, на которое способен такой инструмент.
* **Скорость - цель, а не гарантия.** Scapy через сокет ядра выдыхается
  где-то в районе десятков тысяч кадров в секунду. Скрипт печатает ту скорость,
  которую реально выдал, и если она заметно ниже запрошенной - это сказано
  вслух: устройство на этой скорости не проверено.
* **Урезанные диапазоны названы.** Перебор по /16 - это 65 тысяч кадров;
  генератор режет до 1024 и говорит, что урезал, а не молча шлёт часть.

## Движки

Модель трафика - одно, чем его выдувать в кабель - другое. Транспорт, опрос
хоста, архив прогонов и меню общие; движок меняет только артефакт и то, чем он
запускается.

| Движок | Слои | Состояние |
|---|---|---|
| **Scapy** | L2-L4 | работает: свой скрипт, любой Linux с NIC и root |
| **TRex** | L2-L4 | работает: DPDK, линейная скорость, потери по flow stats |
| **Ixia** | L2-L4 | работает: шасси по IxNetwork REST, счёт по traffic item |
| **JMeter** | L7 | заявлен: потоки, запросы, задержки |

Один профиль - любой движок. Кадр одного и того же профиля уходит в кабель
одинаковой длины везде; это проверяется тестом, потому что иначе два прогона
«одного и того же» теста нечем сравнивать. Считают они по-разному только
потому, что по-разному устроены: Scapy пакует до размера без FCS, TRex так же,
IxNetwork считает размер вместе с FCS - и скрипт добавляет эти четыре байта
обратно, чтобы в кабеле было одно и то же.

JMeter уже выбирается в настройке цели и честно отвечает, чего ему не хватает
на этом хосте, - но гнать через него пока нельзя. Что нужно - ниже, в «Будущих
релизах», и подробнее в `src/traphy/engines/jmeter.py`.

### TRex

Scapy через сокет ядра выдыхается где-то в районе десятков тысяч кадров в
секунду. Выше этого прогон рассказывает про генератор, а не про железку, - и
вот тогда DPDK окупает свою сложность.

Что меняется, когда цель переключена на TRex:

* **Диапазон не разворачивается в кадры.** Перебор по /16 - это четыре байта
  настройки field engine, а не 65 536 кадров в памяти. Scapy такой диапазон
  режет до 1024 и говорит, что урезал; здесь резать нечего, и на экране стоит
  настоящее число.
* **Потери считает железо.** У каждого потока своя группа flow stats, и NIC
  считает её кадры на порту приёма. Это не сниффер, ловящий метку в теле
  кадра, - и потому эта цифра идёт в отчёт без оговорок.
* **Порты вместо интерфейсов.** NIC отданы в DPDK, из `/sys/class/net` они
  пропали; порт адресуется индексом. Форма цели для TRex спрашивает номера, а
  не имена, и списка интерфейсов там нет - его неоткуда взять.
* **Root не нужен.** Демон подняли с ним задолго до нас; скрипт, который им
  управляет, - обычный клиент.
* **Кадры собираются Scapy из самого релиза.** Field engine пишет по
  смещениям, посчитанным против него; чужой Scapy положил бы их мимо, и
  получился бы трафик, который выглядит правдоподобно и не проверяет ничего.
  Поэтому скрипт кладёт control plane релиза в `sys.path` раньше всего.

Чего TRex не умеет, и о чём он говорит вслух, а не молча:

| | |
|---|---|
| Кадр без IP не считается | TRex метит группу полем IP ID; для L2-потока счётчика нет, и прогон помечается «частично» |
| `--count` не работает | TRex шлёт по времени; чтобы послать ровно N кадров, задаётся режим очереди на N |
| Контрольная сумма TCP при переборе портов | не пересчитывается; для UDP вместо неё ставится ноль - законный способ сказать «не считал» |

Цель настраивается так: движок TRex, каталог релиза на хосте, адрес и порт
демона, номера портов отправки и приёма. Опрос цели (`c` в форме) отвечает
тремя отдельными ответами - есть ли каталог, лежит ли в нём control plane,
отзывается ли демон, - потому что это три разные вещи, которые чинят
по-разному.

## Что внутри

```
src/traphy/
  models.py        Profile / Stream / Packet / VMField - вся модель трафика
  presets.py       готовые профили
  codegen.py       Profile → самодостаточный Scapy-скрипт
  codegen_stl.py   Profile → управляющий скрипт для демона TRex
  codegen_ixnet.py Profile → управляющий скрипт для шасси Ixia
  target.py        цель: хост, интерфейсы, движок; хранилище целей
  transport.py     доставка скрипта: локально или по SSH
  probe.py         что есть на цели: NIC, root, Scapy, Java
  runner.py        один прогон: собрать, отправить, разобрать счётчики, записать
  engines/         шов под Scapy / TRex / JMeter
  ui.py            панели, темы, чтение клавиш - только стандартная библиотека
  menu.py          лаунчер
  screens/         настройка цели, сборка трафика, прогон, история
```

Тесты гоняют движок отправки на подменённом Scapy - темп, очереди, смешивание
потоков, перенос по диапазону и подсчёт приёма проверяются без root и без NIC:

```sh
pip install -e '.[dev]' && pytest -q && ruff check src tests
```

## Будущие релизы

Главное, чего тут не хватает, - движок для L7 рядом со Scapy, TRex и Ixia.
Место под него расчищено: транспорт, опрос хоста, архив прогонов и меню общие,
движок меняет только артефакт и то, чем он запускается.

### Ixia

Третий движок и самый непохожий на остальные: трафик выдувает шасси где-то в
стойке, настраивается оно через API-сервер IxNetwork по REST, а клиент крутится
здесь. Цель перестаёт быть машиной, на которой что-то запускается, - это адрес,
карта и порт.

* **Порты назначаются, а не выбираются из списка.** Никакого `/sys/class/net`
  тут нет; порт - это адрес шасси плюс `карта/порт`, и форма цели спрашивает
  именно так.
* **Порт кому-то принадлежит.** Шасси общее, и порт может держать коллега
  посреди своего замера. Отобрать его можно, но это отдельная галка, по
  умолчанию выключенная: без неё занятый порт возвращается с именем владельца,
  а не отбирается молча.
* **Порт приёма обязателен.** Raw traffic item требует обе стороны, так что
  режима «послать и не считать» здесь нет вовсе - каждый прогон на Ixia меряет
  потери по-настоящему просто по устройству, а не по дисциплине.
* **Пароль не хранится.** Linux-серверу нужен логин; пароль берётся из
  `TRAPHY_IXIA_PASSWORD` - не из файла цели и не из командной строки, где его
  видно любому процессу на машине.
* **Неизвестное поле - это отказ, а не пожатие плечами.** Каждое поле кадра
  адресуется своим идентификатором IxNetwork. Если версия называет его иначе,
  прогон останавливается и говорит какое: кадр с тихо оставшимся по умолчанию
  MAC выглядит как трафик, проходит через коробку и отвечает на вопрос,
  которого никто не задавал.

```sh
export TRAPHY_IXIA_PASSWORD=...        # только если сервер спрашивает логин
traphy gen ip_sweep --engine ixia -o sweep.py
```

Чего Ixia не умеет, и о чём говорит вслух:

| | |
|---|---|
| `--count` не работает | число кадров задаётся режимом потока, а не общим счётом |
| Общий pps поверх смешанного профиля | если часть потоков задана в процентах или битах, масштабировать их одним числом значило бы выдумывать - отказывает |
| Случайный перебор | шасси выдаёт свою последовательность, повторить её дословно нельзя |

### JMeter

Scapy и TRex отвечают на вопрос «пропускает ли железка кадры и на какой
скорости ложится». JMeter отвечает на другой - «держит ли сервис за ней N
клиентов с настоящими запросами», - и этот вопрос возникает на тех же стендах,
против тех же целей, обычно сразу после ответа про L2-L4.

Что для этого нужно:

* другая единица нагрузки: не кадры и pps, а thread groups - сколько потоков,
  ramp-up, циклы или длительность, и сам запрос: метод, URL, заголовки, тело.
  `Packet` про это ничего сказать не может, так что рядом встанет своя
  маленькая модель, а не растянутый поверх слой;
* артефакт `.jmx`, а не скрипт: тот же XML, что пишет GUI, чтобы собранный
  здесь план открывался в самом JMeter. В этом и смысл - это должен быть
  настоящий план, а не что-то, запускаемое только этим инструментом;
* другой запуск: `jmeter -n -t plan.jmx -l results.jtl` и JVM на хосте;
  прогресс придётся разбирать из вывода саммарайзера или из `.jtl` по мере
  записи, а не печатать из своего же кода;
* другие счётчики: запросы, ошибки, перцентили задержек и throughput вместо
  tx / rx / потерь. Правило честности остаётся тем же: перцентиль с прогона,
  который не вышел на заданную нагрузку, описывает генератор, а не сервис.

### Что ещё в очереди

| Что | Зачем |
|---|---|
| Перебор MAC | сейчас таблица коммутации нагружается через источники IP; настоящий перебор даст честный стресс CAM |
| Задержка и джиттер | метка времени в payload, чтобы мерить не только потери |
| IPv6 | модель пока только IPv4 |
| Настоящие сессии TCP | сейчас это кадры с флагами, а не установленные соединения |
| Двусторонний прогон | гнать с обеих сторон одновременно и сводить результат |
| Сравнение прогонов | базовый против текущего, чтобы видеть регрессию железки, а не только абсолютные цифры |
| Цели не только Linux | интерфейсы читаются из `/sys/class/net` |
